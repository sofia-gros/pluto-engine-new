## 設計上の判断

### 階層の親参照はメインスレッド走査 (ユーザー承認済み)

カーネルには自チャンクの `ChunkView` しか渡らない (docs/05 §2) ので、親が別のアーキタイプにあると `view.column()` では引けない。実際 `ContainerHandle` は `Transform`/`Parent`/`HierarchyDepth`、`SpriteHandle` は `Transform`/`WorldTransform`/`Sprite`/`SpriteSlot` を持ち、親子でアーキタイプが異なる。そのため:

- **深さ 0 (親なし)**: カーネルで並列計算する (並列化が必要な 100 万スプライトはこのケース)
- **深さ 1〜8**: `transform-system.ts` がメインスレッドで `world.get()` を辿って合成する

`KernelBufferSlot` の追加 (docs/05 §3.2「追加はタスクの指示がある場合のみ」) は行っていない。

### 2 つのシステムに分けた理由

`defineSystem` は `kernel` と `run` のどちらか一方だけを許す (docs/04 §8) ので、「深さ 0 をカーネルで + 深い階層を run で」は 1 つのシステムでは書けない。`order` で順序を保証した 2 システムに分割した。

- `Transform.Root` — order 0、`kernel: RootWorldTransformKernel`
- `Transform.Hierarchy` — order 1、`run: composeHierarchicalWorlds`

### 循環参照の検出はしない (ユーザー承認済み)

循環を作る API が T-5.6 (`ContainerHandle`) の責務なので、そこでのみ `PlutoError(InvalidArgument)` にする (docs/09 §container)。T-2.4 は変換計算のみに責務を絞った。深さ `MAX_HIERARCHY_DEPTH` 超過も同様で、走査は深さ 1〜8 までなので、それより深いノードは親の変換を取り込まない。テストでこの保証を明記した。

## 144FPS の達成 (ディスプレイ 143.98Hz)

当初「ディスプレイが 143Hz なので 144fps は出ない」と考えたが、144Hz と 143.98Hz の差は 0.02Hz で vsync の丸め誤差の範囲だった。**ディスプレイを 143.98Hz に上げたところ 6.940ms (143.99fps) になり、G1 の 144FPS 目標 (6.94ms) を満たした。**

| エンティティ数 | フレーム p50 | fps    | cpuP50 |
| -------------- | ------------ | ------ | ------ |
| 100,000        | 6.940 ms     | 143.99 | 0.44ms |
| 500,000        | 6.940 ms     | 143.99 | 3.02ms |
| 1,000,000      | 6.940 ms     | 143.99 | 4.20ms |
| 2,000,000      | 6.940 ms     | 143.99 | 8.40ms |

`empty` シーンでも 6.940ms なので、フレーム時間は ECS の処理量ではなくディスプレイのリフレッシュレートで決まっている (`cpuP50Ms` は 100 万体で 4.20ms)。**G1 の 144FPS を実際に判定するには、Phase 4 で描画パスが入ってから再検証が必要**。

| エンティティ数 | `spawnChainMs` | `spawnNMs` | 高速化 | set   | get  |
| -------------- | -------------- | ---------- | ------ | ----- | ---- |
| 100,000        | 33.5           | 6.2        | 5.4 倍 | 6.5   | 4.2  |
| 500,000        | 143.5          | 17.0       | 8.4 倍 | 27.2  | 17.0 |
| 1,000,000      | 291.3          | 31.9       | 9.1 倍 | 56.3  | 34.6 |
| 2,000,000      | 564.4          | 64.4       | 8.8 倍 | 133.4 | 75.4 |

**`set` が Firefox 統一で基準 50ms を超えた** (Chrome 31.8ms → Firefox 56.3ms)。`set` は `markRange` を 1 体ごとに呼ぶため dirty 追跡のコストがそのまま出る。基準を 60ms に上げたが、根本対策は `set` でも範囲をまとめてマークする API を追加すること。これは未着手の最適化対象として記録する。
